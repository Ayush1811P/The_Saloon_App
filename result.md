# The Saloon — Complete Development Report

## 1. Project overview

The Saloon is a single-repository salon booking platform with:

- React and Vite website frontend.
- Capacitor-based Android application.
- Supabase authentication, database, RLS, RPCs, realtime, and Edge Functions.
- Customer booking and queue tracking.
- Admin salon operations and staff management.
- Web Push and Android push-notification architecture.
- Shared frontend code packaged into Android as bundled production assets.

The Android app does not use a separate native frontend. It packages the same React/Vite production build used by the website.

## 2. Repository architecture

The repository remains unified:

- `src/` — main React application, customer flows, admin flows, routes, and shared UI.
- `frontend/` — landing-page frontend components.
- `public/` — public web assets and service worker.
- `src/lib/supabase.js` — browser Supabase client.
- `src/services/` — queue tracking and notification services.
- `supabase/` and `booksaloon_supabase/` — backend functions and database migrations.
- `capacitor.config.json` — Capacitor app configuration.
- `android/` — native Android project, Java integrations, permissions, icons, splash resources, and Gradle configuration.
- `.github/workflows/` — independent website and Android automation.

The website remains the source of truth. Android always packages the latest `dist/` output generated by Vite.

## 8. Waiting-time notifications

When a customer books an appointment:

1. The existing Supabase booking RPC creates the booking.
2. The response provides the authoritative booking status and estimated wait.
3. If the status is `WAITING`, the app immediately displays a waiting-time notification.
4. The notification includes the estimated wait and queue-tracking destination.
5. Tapping the notification can open the corresponding customer queue route.

The app also:

- Requests Android notification permission when launched.
- Initializes Android push registration for authenticated customers.
- Registers the FCM token with the existing backend subscription mechanism.
- Uses the `ANDROID` platform identifier.
- Preserves existing Web Push behavior for browsers.

Actual background FCM delivery requires the real Firebase configuration and physical-device testing.

## 10. GitHub Actions automation

### Website workflow

File: `.github/workflows/website-deploy.yml`

- Runs on pushes to `main`.
- Supports manual dispatch.
- Uses `npm ci`.
- Runs the production Vite build.
- Verifies `dist/index.html`.
- Does not deploy to an unconfigured provider.

No Netlify or Vercel configuration was present, so no deployment credentials were invented.

### Android workflow

File: `.github/workflows/android-build.yml`

- Runs independently from website CI.
- Runs on relevant frontend, Android, Capacitor, dependency, and build changes.
- Supports manual dispatch.
- Uses Node.js and JDK 21.
- Configures Android SDK packages.
- Builds the shared frontend.
- Runs Capacitor synchronization.
- Runs `assembleDebug`.
- Verifies the APK.
- Uploads the APK as a GitHub Actions artifact.

The workflows do not wait for each other and do not create an infinite push loop.
